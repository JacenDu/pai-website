PAI architecture ​

This document describes the current content profile and its reference implementation. It is informative. SERVICE.md, FORMAT.md, and HASH.md define protocol and file requirements.

Client and server interface ​

A host application uses a PAI client to exchange content with a selected service. The same service accepts publication requests and exposes published resources to other clients. The service provider operates the server and supplies its account system, storage, and product interface.

The content profile specifies service discovery, supported upload formats, authenticated writes, published resources, snapshots, structured-content responses, file downloads, and source URLs. A platform integrates those operations with its own services. Follo is one potential operator of such a deployment.

The reference server uses a configured set of publisher credentials and filesystem snapshots. A different implementation can use an existing account system and database while providing the same observable protocol behavior. Server integration describes that implementation contract.

Publication and retrieval ​

The client obtains endpoint URLs from the service descriptor. Uploads carry the original ZIP or HTML file bytes. The server validates the file and determines the publisher from the credential.

Ordinary text reads use structured content. Original-image extraction reads the selected version's file. Block source URLs identify a particular publication version so a later update retains the earlier source.

An equivalent publication retry returns 200 and its stored snapshot. Updating a resource uses its declared updateUrl and requires the owning publisher's credential. A new document revision creates the next publication version. The document's edit counter and the server's publication counter have separate meanings; service behavior defines the retry and conflict rules.

Shared document model ​

The content model contains document identity and revision, Markdown content blocks, ordered layout rows, and image assets. A block references each image by asset ID. Layout rows supply reading order and one-, two-, or three-column placement. The renderer chooses fonts, spacing, and responsive breakpoints while preserving the defined content order.

Packaging-only conversion preserves all document fields and original image bytes, including unused assets. It changes their storage representation: ZIP entries use asset paths; HTML embeds Base64 data. Content hashing computes a common digest across these forms.

A .pai file contains the document and original images. Compatible tools supply the parser, renderer, and editor. A complete .pai.html export includes that runtime so a supported browser can open and edit it offline. Data readers extract the JSON without executing the embedded program. The reference service renders uploaded content with its own runtime.

A service can also retain the same content in a database and asset store. The interchange format governs exported and transferred representations; it does not prescribe the database schema.

Node file tools and the browser editor share the parser and validation rules. Browser saving produces a local download. Publishing that saved document is a separate client operation. The protocol does not require a particular editor UI.

Testing instructions, Harness tasks, browser acceptance, and development reports are kept in development/. The public integration guides are Client integration and Server integration.

Planned extensions ​

Open retrieval will build on publication versions, block IDs, asset IDs, and source URLs. The next design work concerns queries, returned excerpts, and how clients identify the material used in an answer. The current content profile provides catalogue and content reads; it has no vector-search or query endpoint.

Hosted-agent interactions will cover a service-operated agent acting within a user's authorized scope, using the material and preferences that user makes available. That work needs explicit authorization and request-result semantics. It remains planned work, with no capability or message schema in the current content draft.
