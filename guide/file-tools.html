PAI file tools and browser editor ​

This directory implements content model 0.6 for both PAI file forms. A .pai file contains document data and original images in a ZIP container. A .pai.html file carries the same content together with rendering and editing code for independent browser use.

The Node CLI, browser editor, and reference service share the file parser and validation rules. File specification · Client integration · Service integration

Build and open ​

Run these commands in the content/ directory:

sh
npm ci
npm run build
npm test

After building, open dist/service.pai.html, dist/event.pai.html, or dist/guide.pai.html in a browser. These generated files are excluded from Git. Browser edits are saved as local downloads.

Edit a document ​

The current editor uses Chinese labels. 编辑 enters editing, and 完成 (Done) saves changed content as .pai.html and returns to reading. With no changes, it returns without a download. An active block has a light boundary; text paragraphs have no separate inner focus frame.

The block menu contains Appearance, Width, Copy, Cut, AI, and Delete icons. Appearance opens the color palette and background-image icons. The width icon shows the next action: widen a reading-width row or narrow a page-width row. Width applies to the whole row. Icon tooltips show the action and relevant shortcut or Markdown syntax; keyboard focus also displays them.

Block copy and cut carry text, formatting, background settings, and referenced images. Pasting in the editor creates a new block ID and retains the original image bytes. Cut removes the source only after copying succeeds; undo restores it. Clipboard access is required.

The text toolbar starts with paragraph type and alignment controls, each with a dropdown indicator. Paragraph types appear in a horizontal icon menu; narrow screens wrap the choices. The alignment menu offers left, center, and right alignment for complete selected paragraphs or headings. Drag the toolbar handle to reposition it. Text color and highlight apply to selected characters.

New links use a URL field beside the selection. A bare domain such as example.com becomes https://example.com/. Clicking an existing link in edit mode shows its URL, Edit, and Unlink. Edit allows changing the displayed text and destination together; changing only the URL retains the text's existing formatting. Unlink retains the displayed text. Enter applies changes; Escape closes the panel. These settings survive both file representations.

Splitting, joining, or deleting blocks recalculates the affected rows' default widths. The editor uses a preferred column width of 320 px and a 32 px gap: required width = 320 / smallest column share + 32 × (columns − 1). Rows requiring at most 760 px use reading width; larger rows use page width. Equal two-column rows therefore use reading width, and equal three-column rows use page width. Existing documents retain their saved widths when opened.

Manual width and column-ratio changes persist until row membership changes. Reordering within a row carries each block's width proportion with it. Moving a complete row preserves its width. A newly joined block receives the average weight of the destination's existing columns. At narrow viewport sizes, a row stacks in document order when its smallest column would be less than 14 times the body font size. The saved layout remains unchanged.

In a multi-column layout, the content plus button has priority in its hit area. Adjacent gaps remain available for column resizing. Image placement changes update layout parameters without re-encoding the original image.

Between rows, move the pointer into the gap to reveal an insertion line and a circular plus button in the canvas's right margin. Its horizontal position stays fixed across reading-width, page-width, and multi-column rows. Only the plus button inserts a blank, single-column row. The editor focuses the new block and hides the insertion line until the pointer moves. Keyboard focus also reveals the control. Touch layouts keep the plus visible with a 44 × 44 px target. The line sits above the following row's block handles; the plus target stays to their right. Row spacing is the same in reading and editing modes, and hovering does not change the layout.

Press Enter to continue writing within a block. Use the content-side plus or / for paragraphs, headings, images, and tables. Create an independent block when its content needs its own position or background.

The top bar uses the official .pai logo and icon controls. Reading mode provides Edit, Export, New, and Details. Editing mode provides Undo, Redo, Done, New, and Details. 详情 (Details) lists page color, mobile preview, AI context, and shortcuts with icons and text. Page color opens a second panel containing six presets, a native color picker, and a HEX input. The presets are white, warm white, light gray, light sand, pale blue, and charcoal. HEX input accepts three or six hexadecimal digits, with an optional #. Color changes support undo and persist in both file forms. The footer links the official PAI logo to the project website and describes publication through compatible services and human–AI content use.

Markdown-style input supports heading, list, and quote prefixes. Bold, italic, inline-code, and link syntax converts after a space. Type / on an empty paragraph to add content, or three backticks followed by Enter to start a code block. Editing remains in the document view.

Open, save, and export ​

Open a .pai.html file directly in a browser. 新建 (New) opens the system save-file picker before creating a blank document. Select a filename and location, then enter the document title in the first heading. Done and Cmd/Ctrl+S require a nonempty title. The browser may create an empty file or truncate a selected existing file when the picker is confirmed. The editor writes document content only after a title is entered. The standalone editor has no file-import menu. Use the CLI to convert a .pai file to .pai.html.

For a newly created document, 完成 (Done) writes the document to the selected .pai.html file and exits editing. Subsequent saves in that session update the same file, including after a title change. Cmd/Ctrl+S saves without leaving editing mode. The system picker handles confirmation when an existing filename is selected.

The selected file handle remains in memory for the current session; they are not embedded in the document. Existing files opened directly in a browser save by download. In reading mode, 导出 (Export) provides .pai.html, .pai, PDF printing, and Markdown downloads. Downloaded filenames include the document ID and revision.

The browser controls the download location and retention. The page cannot confirm whether a download was cancelled. Saving preserves all images in the asset table, including images not currently referenced by a block. A local write is marked saved only after the writable stream closes successfully. If serialization or writing fails, or editing continues during the save, Done keeps the document in editing mode with those changes unsaved.

With unsaved changes, New offers 保存并新建 (Save and create) or 不保存 (Discard). Both actions select the next file before replacing the current document. Save and create then saves the current document. Cancelling the picker, closing the confirmation, or editing during the operation preserves the current document.

File selection requires a browser implementing showSaveFilePicker() and a user-initiated click. Browsers without this capability leave the current document open and display an explanation. The implementation calls the picker before asynchronous serialization to retain user activation.

A standalone HTML file contains the editor version used at export time. To update its editor, use CLI convert with --template pointing to a newly built .pai.html. A supported browser can read, edit, and save the standalone file offline. Attachment previews that do not execute scripts cannot render the current file; download it and open it in a browser.

Saving from a published reading page also creates a local download. Use the publication client to upload an update. Existing version links continue to identify the previously published content.

AI and programmatic editing ​

The AI icon copies the source location, document ID and revision, block or selection position, and current content directly to the clipboard. A toast confirms the copy. Users append the requested change in their own AI tool. Selection and block controls use the same icon. The prompt omits image encoding and editor code; the document does not retain a local filesystem path.

The CLI supports structured processing of both file forms:

sh
node cli.mjs inspect dist/service.pai.html
node cli.mjs inspect dist/service.pai.html offer-b
node cli.mjs asset dist/service.pai.html hero -o hero.svg
node cli.mjs convert dist/service.pai.html -o service.pai
node cli.mjs inspect service.pai
node cli.mjs text service.pai
node cli.mjs text service.pai offer-b
node cli.mjs patch service.pai change.json -o edited.pai
node cli.mjs convert edited.pai -o edited.pai.html
node cli.mjs hash edited.pai

inspect includes text and asset descriptions while omitting image encoding and the editor program. A container-only conversion preserves the document ID, revision, blocks, and every image. A successful content patch increments the revision. File writes use a temporary file and replace the target only after the write succeeds.

text writes Markdown in layout reading order, optionally selecting one block. It preserves pai: image references; asset retrieves their original bytes. Both commands validate the input file before extracting their result.

Converting ZIP to HTML uses dist/service.pai.html as the default complete editor template. Specify another complete template with --template template.pai.html. An HTML input uses its existing shell by default. The template must carry the styling and code needed to run independently; the data parser verifies the content entry point rather than executing the template.

Patch operations are applied as one batch against baseRevision. Supported operations are replaceRegion, setBackground, moveRegion, insertRegion, deleteRegion, setLayout, reorderRegions, reorderSections, and setBackgroundImage. For example, save this as change.json for a document at revision 0 with an intro block and hero asset:

json
{
  "baseRevision": 0,
  "operations": [{
    "type": "setBackgroundImage",
    "id": "intro",
    "image": {"asset":"hero","x":50,"y":50,"overlay":0.65,"shade":"#ffffff"}
  }]
}

Use "image": null to remove a background image. A stale baseRevision or an invalid operation rejects the whole patch.

The browser and Node implementation share these limits: 64 MiB input or total expanded ZIP data, 4,096 ZIP entries, and JSON nesting depth 256. Python is used for independent ZIP checks in tests; production file processing does not require it.

Content representation ​

The reference file API returns image data as Uint8Array. ZIP reads retain extracted binary bytes; HTML reads decode embedded Base64. Writers also accept existing Base64 document objects. ZIP writes use binary assets, and standalone HTML serialization encodes them as Base64. Content model 0.6, ZIP packaging 1, and the defined content hashes remain unchanged.

js
import {readPaiFile, writePaiFile, getAsset, toJSONDocument} from './src/file.mjs';
import {readMarkdown, inspectDocument} from './src/document.mjs';

const {document} = await readPaiFile(fileBytes);
const text = readMarkdown(document);          // Markdown in layout order
const block = inspectDocument(document, 'intro'); // No image bytes
const image = getAsset(document, 'hero');     // Detached Uint8Array
const saved = await writePaiFile(document, {format: 'pai'});
const json = toJSONDocument(document);       // Base64 representation for JSON

Use toJSONDocument() before serializing a complete in-memory document as JSON. toBinaryDocument() converts an existing Base64 document. getAsset() returns a byte copy; replace asset objects when editing a document. ZIP writing captures owned resource bytes before asynchronous compression, so subsequent caller mutations do not change the saved snapshot.

Validation reuses image-reference analysis for unchanged Markdown. A changed block is parsed again; asset references and layout are checked against the current document on every validation. readMarkdown() and inspectDocument() operate on an already loaded, validated document without accessing image data. Initial file import still validates the complete package, and saving writes a complete file. Network publication remains a complete upload.

A .pai ZIP stores document.json and original image entries. The authoritative data in .pai.html is the JSON in <script id="pai-data" type="application/json">. Both forms use block Markdown, ordered layout arrays, and a shared asset table. The local tools can migrate legacy 0.4 and 0.5 HTML data on import; publication requires content model 0.6.

An image instance can carry a placement ID, width percentage, and alignment:

md
![Image description](pai:hero){pai-image:img_one width=60 align=center}

A block with a background image has a minimum height of 12 rem in the reference editor and grows with its content. Background settings preserve the block’s text and inline images.

The same asset can appear at different widths and positions. A block's backgroundImage stores its asset ID, crop focus, overlay opacity, and overlay color. An empty paragraph is represented by <!--pai:blank--> on a line of its own. See the format specification for field definitions and validation rules.

Automated checks ​

From the project root, run npm run verify for file, specification, and service checks. Run npm --prefix content test for the file and editor unit tests.
