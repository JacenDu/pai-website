Server integration ​

A PAI server implements the content operations described in SERVICE.md. A service provider can integrate these operations into an existing platform. Its account system issues publisher credentials, its storage retains documents and versions, and its product supplies any online editing interface.

The reference server demonstrates the wire behavior using a local credential file and filesystem snapshots. It listens on loopback. The instructions below operate from the PAI project directory after installation.

Run the reference server ​

Create a private local credential file:

sh
mkdir -p .local
node --input-type=module <<'NODE'
import { randomBytes } from 'node:crypto';
import { writeFileSync } from 'node:fs';
const entries = [{ publisherId: 'demo:alice', token: randomBytes(32).toString('hex') }];
writeFileSync('.local/publishers.json', JSON.stringify(entries), { flag: 'wx', mode: 0o600 });
console.log('Created .local/publishers.json');
NODE

The command fails if that file already exists, preserving its credentials. The file contains an array of {publisherId, token} entries; add another entry to give a second publisher an independent credential. Both publisher IDs and tokens must be unique in the reference configuration.

Start a service on port 4747:

sh
PAI_PUBLISHERS_FILE="$PWD/.local/publishers.json" \
  node src/provider.ts 4747 content .pai-data/content

The startup line contains the actual service URL. Passing port 0 selects an available local port. The final argument is the snapshot directory. Reuse that directory to retain documents and historical versions after a restart. Stop the server with Ctrl+C.

In another terminal in the same directory, set the client credential without printing it:

sh
export PAI_TOKEN="$(node -p "JSON.parse(require('node:fs').readFileSync('.local/publishers.json','utf8'))[0].token")"
npm run publish -- http://127.0.0.1:4747 content/dist/event.pai

The configured publisher is returned in the publication response. Public GET requests need no credential. PAI_OWNER_ID and PAI_OWNER_TOKEN remain available for the single-publisher local trial; a client normally uses PAI_TOKEN.

Implement the content profile ​

Start with the discovery schema and fixed exchanges. The following table maps protocol behavior to platform integration work.

AreaImplementation work
DiscoveryServe /.well-known/pai.json; declare the supported protocol, capabilities, formats, authentication, and operation URLs
AuthenticationResolve the write credential to a publisher; check the selected resource's ownership for PUT
File ingestionParse ZIP or HTML data without executing uploaded code; validate the content model and image references
Identity and versionsMaintain a resource for each publisher/document pair; retain immutable snapshots and the latest-version pointer
RetriesCompare document revision and canonical content; return the stored snapshot for an equivalent retry
RepresentationsSupply versioned structured content, the original file, and a reading page
SourcesKeep block source links bound to their publication version and original images
ErrorsReturn the specified HTTP status and machine-readable error code

The common content model is the interoperability boundary. A server can store its data in a database and images in object storage. The reference server's directory layout is an implementation detail.

Publication preserves the first file stored for a snapshot. A cross-container retry returns that same snapshot and original file. Use downloadFormat and downloadMediaType to describe its actual form. The reading page can use the server's own renderer and editor. The reference implementation generates it from validated data using the bundled editor, without executing uploaded HTML programs.

Apply the content hash rules when comparing versions. Image bytes participate in content identity; ZIP compression bytes and the HTML editor program do not. Preserve the historical hash algorithm marker when returning an older snapshot.

For network deployment, serve the origin over HTTPS and connect authentication to the platform's credential lifecycle. The reference process binds to 127.0.0.1; a deployment can place it behind a same-origin reverse proxy. The current client expects /.well-known/pai.json at the origin root and follows same-origin operation links.

The reference implementation limits an upload, ZIP-expanded data, and generated reading HTML to 64 MiB each. Its file tools also limit ZIP entries and JSON depth. These are implementation limits, not a protocol-wide storage quota. A deployment should document its own limits and return the specified error when it rejects a file.

Check an implementation ​

Run the checker against an HTTPS origin or a loopback HTTP origin:

sh
node src/check-service.ts http://127.0.0.1:4747
node src/check-service.ts http://127.0.0.1:4747 \
  --resource http://127.0.0.1:4747/resources/RESOURCE_ID \
  --output read-report.json

Replace RESOURCE_ID with a returned resource ID. Default checks perform public reads, select the requested resource or the first catalogue item, and inspect discovery, declared links, resource/version metadata, structured content, the downloaded file, content hashes, assets, source-link origins, and availability of the reading representation. An empty catalogue is reported as skipped content checks. Browser verification checks whether a source link reaches the intended block and whether the document renders correctly.

Exercise writes on a test deployment:

sh
node src/check-service.ts http://127.0.0.1:4747 --write --output write-report.json

--write requires PAI_TOKEN. It publishes a uniquely identified synthetic document, retries with the other container when supported, and tests updates and historical reads when advertised. Test resources remain in the service; the current draft has no deletion endpoint. Use a dedicated test publisher or test service for repeated runs.

The report is JSON on standard output. --output writes the same report to a new file and rejects an existing path. Exit status is 0 when the performed checks pass, 1 when a check fails, and 2 for invalid command usage. Reports list skipped operations when the corresponding capability or material is unavailable.

The checker follows declared links, refuses redirects and cross-origin links, and sends the token only with explicit write operations. It checks the content profile behavior covered by its report. Visual quality and editor interactions use the separate browser acceptance suite; a passing report is not a complete deployment audit.

Keep the implementation aligned ​

Run the fixed specification tests and the service tests after changing ingestion, authorization, revision handling, or response generation:

sh
npm run check:spec
npm test

Record the protocol version, supported content/container versions, and deployment limits with each release. Changes to platform accounts, storage, or editor internals can stay within the same protocol version when the externally observable requirements continue to hold.
