PAI Content Service ​

Protocol version: 0.1.0-draft.1 · Profile: content

A PAI client publishes a document to a server. The server stores publication versions and exposes text, original images, and source URLs. Developers can implement these interfaces in their own platforms. A service provider, including Follo, operates an implementation of the protocol.

The conformance language applies. Field definitions are in service.schema.json; document validation is defined in FORMAT.md. Terminology defines the roles and version identifiers.

Implementation note: the reference server implements this content profile. Development records contain implementation checks and test handoff material.

Publication example ​

The client reads the service descriptor, obtains the publication endpoint and supported formats, and uploads the complete file with a publisher credential:

http
POST /documents HTTP/1.1
Host: provider.example
Authorization: Bearer example-credential
Content-Type: application/zip

<raw bytes of event.pai>

/documents is an example path. The client uses the URL returned by discovery. A first publication returns 201 and a resource object containing reading, download, content, and update URLs. Other clients retrieve the content and use each block's sourceUrl to cite that publication version.

A document has a persistent document.id and a local integer revision. A server creates a published resource for a publisher's document. That resource has a server-assigned id and publication version, starting at "1". Each stored publication version is a snapshot. Document revisions and publication versions are separate counters.

Discovery ​

The client is configured with the selected service origin. It sends an unauthenticated GET to /.well-known/pai.json at that origin:

json
{
  "protocol": "pai",
  "version": "0.1.0-draft.1",
  "profile": "content",
  "capabilities": ["document-publication", "document-update", "content-read"],
  "formats": [
    {"id": "pai-zip-v1", "mediaType": "application/zip", "contentVersion": "0.6"},
    {"id": "pai-html-v0.6", "mediaType": "text/html", "contentVersion": "0.6"}
  ],
  "authentication": {"scheme": "Bearer"},
  "contractUrl": "/spec/SERVICE.md",
  "endpoints": {"documents": "/documents", "resources": "/resources"}
}

profile: "content" selects the rules in this specification. The profile includes content-read, which provides the resource catalog, metadata, structured content, file downloads, and reading pages. document-publication advertises file publication; document-update advertises updates through resource-specific URLs. A server MUST advertise only capabilities and input formats it implements. A server advertising document-publication MUST provide endpoints.documents. endpoints.resources is REQUIRED.

formats describes accepted new uploads. Historical snapshots are read using their recorded download format, including formats no longer accepted for new uploads.

Clients MUST follow URLs returned by discovery and resource responses. Example paths are not fixed endpoint paths. A URL is either root-relative, starting with a single /, or an absolute HTTP(S) URL at the discovery origin. Origin consists of scheme, host, and port. Root-relative URLs use the discovery origin; URLs beginning with // are invalid. All endpoint, reading, download, and source URLs MUST be same-origin. Clients MUST verify the origin of response links and redirect targets. Bearer credentials MUST be sent only with writes to the selected service.

Clients MUST check the protocol version before issuing operations. They SHOULD report an unsupported version or missing capability. Clients MAY ignore unknown response fields. Unknown fields MUST NOT grant permissions or change the meaning of known fields.

Authentication and ownership ​

Discovery, catalogs, published resources, structured content, reading pages, and downloads are publicly readable. POST publication and PUT updates MUST use Authorization: Bearer <credential>. The server MUST determine the publisher from the credential and return that identity in publisherId. A user-supplied identity in the uploaded content MUST NOT establish publication ownership. Author attribution is part of the content.

Network services MUST use HTTPS for Bearer credentials. Loopback development services MAY use HTTP. Credential issuance is managed by the service provider; this profile specifies credential transport and validation.

Publisher IDs and resource IDs are scoped to a service. External references use the returned URLs. A document ID travels with the file; publication to another service can produce a different resource URL.

POST publication ​

The client sends a POST to endpoints.documents with the complete raw file as the request body. .pai uses Content-Type: application/zip; .pai.html uses Content-Type: text/html; charset=utf-8. The request has no JSON or Base64 wrapper around the file.

The server MUST validate the credential, media type, packaging, and common document data. Data extraction MUST NOT execute scripts in the uploaded file. pai-zip-v1 reads document.json and asset entries; pai-html-v0.6 reads pai-data and embedded images. Both use content model 0.6.

The server identifies an existing resource by authenticated publisher and document ID. The same publisher's document retains one resource ID. Different publishers can publish the same document ID under their own resource records.

Implementation note: the reference service limits each upload, total expanded ZIP data, and generated reading HTML to 64 MiB. Exceeding a limit returns 413 payload_too_large without creating a version. Deployments can publish different limits.

PUT update ​

To update a selected resource, the client MUST send a PUT to that resource's updateUrl. The media type and body follow the POST rules.

The server MUST establish that the target exists and belongs to the authenticated publisher before validating the file. A target belonging to another publisher returns 403 forbidden. A document ID that does not match the target returns 409 document_id_mismatch. A failed PUT MUST NOT create another resource. An updateUrl always identifies the same resource; using the URL from a historical snapshot applies the revision rules below to that resource's current state.

Revisions, retries, and hashes ​

Publication versions are decimal strings beginning with "1" and increasing by one for each new snapshot. Document revision is a nonnegative safe integer incremented by content edits. For example, a document first uploaded at revision 5 receives publication version "1". Packaging-only conversion preserves document ID and revision.

The server MUST apply these rules:

Uploaded documentResult
The publisher has no resource for this document ID201; create a resource and its first snapshot
The revision exists and content is equal200; return the saved snapshot for that revision, including a historical revision
The revision exists and content differs409 document_revision_conflict
The revision is higher than the current highest revision201; create the next snapshot of the same resource
The revision is lower than the current highest revision and was never published409 stale_document_revision

A retry MAY use the other packaging format. The server compares common content and reuses the original snapshot and first saved file. A retry MUST NOT replace the file, create a version, or change the current-version pointer. Concurrent submissions of the same revision and content MUST produce only one snapshot. Historical text, images, and block source URLs MUST retain their original content.

New snapshots use pai-content-sha256-v1. document.contentHash is the lowercase hexadecimal SHA-256 digest; document.contentHashAlgorithm identifies the algorithm. HASH.md defines the calculation and expected fixture results. ZIP bytes, compression settings, and the HTML runtime are excluded from content comparison.

Legacy 0.0.6 snapshots retain their hashes and use pai-json-sha256-v0.6. Hashes from different algorithms MUST NOT be compared directly. For a historical retry, the server compares the uploaded and stored documents using one common normalization rule, then returns the original snapshot with its original hash and algorithm.

Resource responses ​

Successful POST and PUT responses contain a resource object. Its REQUIRED id, string version, publisherId, and title identify the returned snapshot. Its document contains document ID, revision, title, format: "pai", version: "0.6", content hash, and algorithm.

FieldMeaning
urlResource URL; GET returns its latest version
updateUrlPUT endpoint; REQUIRED when the service advertises document-update
versionUrlImmutable snapshot URL; GET returns this version's resource object
previousVersionUrlPrevious publication version's URL; null for version 1
representations.readingReading page for this snapshot
representations.downloadComplete file first saved for this snapshot
representations.contentStructured content in reading order
downloadFormatStored packaging: pai-zip-v1 or pai-html-v0.6
downloadMediaTypeCorresponding application/zip or text/html

All listed fields except conditionally required updateUrl are REQUIRED. Representation fields are URL strings. On a retry using another packaging format, the download format remains that of the first saved file. A download MUST use a Content-Type matching downloadMediaType and an attachment Content-Disposition. The reading page renders the common content of the snapshot.

Resource responses provide publication metadata and retrieval URLs. Text is retrieved from representations.content. The reference content service omits the historical duplicate content field from resource responses.

GET endpoints.resources returns { "items": [resource, ...] }, using the latest version of each resource. Catalog order is unspecified and titles can repeat. Clients identify resources by ID or returned URL.

Structured content and citations ​

The content endpoint returns {resource, document, blocks, assets}:

  • resource contains id, version, and url. Its url identifies this snapshot's versionUrl.
  • document matches the snapshot's document metadata.
  • blocks follows the document reading order. Each block contains id, markdown, and sourceUrl.
  • assets maps image IDs to mime, name, and original-byte bytes.

When a source block uses a background image, its structured block MUST include backgroundImage: {asset, alt?}. asset references the same-version asset map. An existing source alt MUST be preserved. Position, overlay, and color remain in the complete document file.

Asset name is copied from the source document. If absent, the structured response uses the asset ID as a display name. This fallback MUST NOT modify the source document or its content hash.

A citation uses the selected block's sourceUrl unchanged. That URL identifies the block in the snapshot's reading page. Retaining document ID and revision, resource ID and version, and block ID allows a client to locate the exact cited content. The same identifiers support repeated image occurrences and documents with equal titles.

Original image retrieval ​

A Markdown pai:<assetID> reference or backgroundImage.asset is interpreted within its document version. Starting from structured content, a client can follow resource.url to obtain that snapshot's download URL. It then follows representations.download and reads downloadFormat:

  • pai-zip-v1: read document.json, obtain its document, and read the ZIP entry at document.assets[assetID].path.
  • pai-html-v0.6: parse the JSON in <script id="pai-data" type="application/json">, then Base64-decode assets[assetID].data.

The client MUST verify document ID and revision against the response before using the data. Asset MIME and actual byte length MUST match the structured-content metadata. HTML scripts need not execute. ZIP paths and validation follow FORMAT.md. Multiple references to an image retain the same asset ID; each block's sourceUrl identifies its context.

Implementation note: the reference client downloads and validates the complete file to extract an image. Its binary in-memory asset representation leaves this retrieval flow and all HTTP representations unchanged. Individual-image endpoints and network patch operations are outside the current content profile.

An error response contains JSON { "error": "code" } and MAY include a human-readable message. Clients use HTTP status and error for programmatic handling.
