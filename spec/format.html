PAI Content Model and File Packaging ​

2026-11-09 · Draft 1 · Content model 0.6 · ZIP packaging 1

This specification defines document text, layout, image assets, and their storage in .pai and .pai.html files. Both representations contain the same document. Conversion MUST preserve text, layout, original images, document ID, and revision.

The conformance language applies. Terminology defines the document and interface terms. The document schema uses JSON Schema 2020-12. Its https://pai.example/ identifiers are placeholders. HASH.md defines content comparison across file representations.

Document structure ​

A document has three structural components:

  • Content blocks, stored in regions, contain Markdown and optional background styling. A block can be arranged or moved as a unit.
  • Layout rows, stored in sections, arrange one to three blocks and specify their order and relative widths.
  • Image assets, stored in assets, contain original images. Text and backgrounds reference them by asset ID. An asset can be used more than once.

This complete document has one text block in a single-column row:

json
{
  "format": "pai",
  "version": "0.6",
  "id": "weekend_event",
  "title": "Weekend event",
  "revision": 0,
  "background": null,
  "regions": [
    {"id": "intro", "markdown": "# Weekend event\n\nJoin a walk on Saturday afternoon.", "background": null}
  ],
  "sections": [
    {"id": "row_1", "regions": ["intro"], "columns": 1, "weights": [1], "width": "reading"}
  ],
  "assets": {}
}

HTML stores this object directly in pai-data. ZIP stores it in the document member of document.json. ZIP stores image bytes as separate entries; HTML embeds Base64-encoded image bytes in the data object.

All document fields in this table are REQUIRED:

FieldValue
format"pai"
version"0.6"
idDocument ID, preserved across conversion, renaming, and relocation
titleString; an empty string is valid
revisionInteger in 0..9007199254740991
backgroundSix-digit hexadecimal color #RRGGBB, case-insensitive, or null for the renderer's default page background
regionsArray containing at least one content block
sectionsArray containing at least one layout row; determines reading order
assetsObject mapping asset IDs to image asset objects; {} is valid

IDs MUST match [A-Za-z0-9_-]+ and MUST NOT equal __proto__, constructor, or prototype. Block IDs MUST be unique within regions; row IDs MUST be unique within sections. Asset IDs are keys in the asset object. These are separate identifier namespaces.

The core structure is closed: fields not defined by this specification are invalid. JSON object member names MUST be unique. Strings MUST contain valid Unicode without unpaired surrogates. Numbers MUST be finite JSON numbers.

Blocks, rows, and reading order ​

A block has three REQUIRED fields: id, markdown, and background. markdown is a string and MAY be empty. background is a six-digit hexadecimal color or null; null exposes the page background. backgroundImage is OPTIONAL and is defined below. An empty document retains one empty block and a row referencing it.

All row fields are REQUIRED:

FieldConstraint
idValid row ID
regionsBlock IDs in display order; length equals columns
columnsInteger 1, 2, or 3
weightsSame length as regions; each value is in 0.2..5 and denotes relative column width
width"reading" or "wide"

Every block MUST occur in exactly one row, exactly once. Every block reference MUST resolve. The top-level regions array stores block objects; reading order is determined by sections and each row's regions array.

Rendering and structured-content extraction MUST use the same order: rows in array order, then blocks in each row's array order, then Markdown nodes within each block. Lists retain item and nested-content order; block quotes retain their internal order; tables are read row by row, then cell by cell. Text, links, inline code, and images retain their inline order. Code blocks preserve their content and line breaks. A narrow viewport MAY stack columns vertically while retaining this sequence.

reading denotes a width suitable for continuous text, and wide denotes the wider page area. Pixel dimensions, fonts, spacing, and responsive breakpoints are renderer choices.

Implementation note: the reference editor uses a 760 px reading width and a 1160 px maximum page width. It selects wide for multi-column rows. The content model also permits reading with one to three columns to retain existing 0.6 documents.

Markdown and image occurrences ​

Block text uses CommonMark with simple pipe tables. Supported constructs include headings, paragraphs, emphasis, strong emphasis, links, images, inline code, fenced and indented code blocks, lists, block quotes, thematic breaks, and line breaks. Table cells contain inline content; header separators express left, center, or right alignment. Raw HTML is treated as text. Code is stored as content and is not executed.

Implementation note: the reference parser uses markdown-it with the commonmark preset and the table rule enabled.

PAI adds two syntactic forms:

markdown
<!--pai:blank-->

![Image description](pai:image_01){pai-image:occurrence_01 width=75 align=center}

An isolated <!--pai:blank--> line denotes an explicit empty paragraph, including inside a list. Repeated markers preserve repeated empty paragraphs. Ordinary consecutive blank lines retain Markdown behavior.

An image suffix immediately follows the image. Its fields occur in the order shown above. The occurrence ID uses the general ID syntax and MUST be unique within its block. width is a decimal number matching [0-9]+(?:\.[0-9]+)?, expressing a percentage of the block content width; it MUST be greater than 0 and at most 100. align is left, center, or right. Without a suffix, width is 100, alignment is center, and the occurrence ID is absent. The occurrence ID identifies one placement; the asset ID identifies the original image.

A parser recognizes only the complete suffix syntax, then validates its width and occurrence ID. Unmatched text remains ordinary Markdown. For example, align=unknown remains text after the image. width=101 matches the syntax but fails the range constraint.

Image destinations MUST use pai:<assetID> and MUST reference an existing asset. Ordinary hyperlinks retain their destinations. Both foreground and background images are included in the file. Markdown semantic validation checks suffixes and asset references; JSON Schema checks only that markdown is a string.

Background images ​

A block's optional backgroundImage object has five REQUIRED fields:

FieldConstraint
assetExisting image asset ID
x, yPercentages in 0..100 specifying background position; rendering covers the block while retaining image aspect ratio and cropping overflow
overlayOverlay opacity in 0..1; 0 is transparent and 1 is opaque
shadeSix-digit hexadecimal overlay color; null is invalid

The object MAY include an alt string describing the image. Removing a background removes the whole backgroundImage member. Background assets appear in the asset inventory; Markdown determines the block's text reading order.

Implementation note: the editor preserves the foreground image description as alt when converting an image to a background.

Asset metadata and bytes ​

An asset's REQUIRED mime is one of image/png, image/jpeg, image/webp, image/gif, or image/svg+xml. Optional name is a string; its absence is preserved. Optional bytes is a nonnegative safe integer and, when present, MUST equal the decoded or extracted byte length.

An asset MUST contain exactly one of data and path. HTML uses data: standard Base64 with padding and no line breaks. ZIP uses path, as defined below. All assets in one file MUST use the representation required by its container. For an empty asset object, the container determines the packaging.

Original image bytes are the basis for saving and conversion. Packaging-only conversion MUST preserve every asset, including unreferenced assets. Blob URLs or temporary rendering URLs MUST NOT replace asset IDs in saved content. Transcoding, recompression, and asset removal are content edits.

Standalone HTML: .pai.html ​

An HTML file uses UTF-8 and contains one data element:

html
<script id="pai-data" type="application/json">{"format":"pai","version":"0.6",…}</script>

The ellipsis is illustrative. The actual element MUST contain a complete JSON document object without the ZIP wrapper. Every asset uses data and has no path. Writers MUST escape < in JSON as \u003c to keep content inside the data element.

A complete standalone HTML export MUST include the styles and runtime required for rendering and editing, plus all image data. In a browser supporting that runtime, it SHOULD support offline viewing, editing, export, and reopening. Ordinary hyperlinks MAY refer to network resources. Optional decorative resources, such as external fonts, MAY use the network; core rendering and editing remain available locally.

The data element is parsed as HTML. Attribute order, quote style, and tag-name casing follow HTML syntax. The actual document MUST contain exactly one element with id="pai-data". It MUST be an HTML-namespace script with a complete closing tag, no src, and a type value equal to application/json after trimming whitespace and converting to lowercase. Duplicate attributes on this element are invalid. Comments and elements inside template content do not supply the document data element.

A data reader extracts the JSON without executing the included runtime. A service processes uploaded content using its own parser and renderer. Runtime updates and HTML whitespace are packaging changes. Data validation establishes that the document is readable; a complete standalone export also needs the offline browser behavior above.

Implementation note: the conversion tools use an existing complete editor template. They retain the rest of the selected template and replace the data element with the standard form shown above.

ZIP packaging v1: .pai ​

The container is ZIP and uses the .pai filename extension. Its UTF-8 entry point is document.json. The root object contains exactly container and document:

json
{
  "container": {"format": "pai-zip", "version": "1"},
  "document": {
    "format": "pai",
    "version": "0.6",
    "id": "example",
    "title": "Example",
    "revision": 0,
    "background": null,
    "regions": [{"id": "intro", "markdown": "![Description](pai:photo)", "background": null}],
    "sections": [{"id": "row", "regions": ["intro"], "columns": 1, "weights": [1], "width": "reading"}],
    "assets": {"photo": {"mime": "image/png", "path": "assets/photo"}}
  }
}

The package schema validates the wrapper and references the common document schema. An asset's path MUST equal assets/<assetID>. It has no extension; mime specifies the image type. A corresponding binary ZIP entry MUST exist. File entries MUST be exactly document.json and the entries referenced by the asset object. Optional directory entries are limited to ./ and assets/; readers ignore them and writers MAY omit them.

ZIP v1 uses Store (method 0) or Deflate (method 8), a single volume, and no encryption. Entry names MUST be unique. The document and asset entries MUST be regular files. Paths use /; the fixed path rules exclude absolute paths and parent traversal. Directory entries MUST contain no data.

Readers MUST validate entry sizes and CRC values, asset references, and optional bytes. Missing entries, duplicate names, mismatched resource paths, and corrupt compressed data are invalid. Entry order, timestamps, and the choice between Store and Deflate do not change the document content.

The fixtures contain actual ZIP files and their expanded data objects.

Conversion, edits, and versions ​

Packaging-only conversion MUST preserve common fields, array order, exact Markdown strings, asset metadata, and original image bytes. Adapters replace data with path or vice versa. Document ID, revision, and object IDs remain unchanged. An absent name, bytes, or alt remains absent. The hash algorithm derives byte lengths as specified in HASH.md.

Conversion MUST preserve unreferenced assets. Saving edited text or assets produces a new document revision. Updating the HTML runtime or recompressing ZIP leaves the revision unchanged.

Content model version (document.version), ZIP packaging version (container.version), editor release version, and service protocol version describe different components. HTML retains the existing data element and has no additional container object.

Implementation note: the file tools accept patches containing baseRevision and operations. They check the base revision, apply the batch to a copy, validate the result, and increment the revision once after success. Failure leaves the original document unchanged. Existing operations edit blocks, layout, backgrounds, ordering, and images. This is a local tool interface; service writes follow SERVICE.md.

Historical HTML content models 0.4 and 0.5 are migrated to 0.6 by the local tools. Current service uploads accept content model 0.6; older documents can be converted before publication.

Reference implementation limits ​

This section is informative.

The Node tools and browser editor use the same file module. Current limits are 64 MiB per input file, 64 MiB total expanded ZIP data, 4096 entries, and JSON nesting depth 256. A service provider can publish different processing limits.

The reference readPaiFile() API returns image data as Uint8Array. HTML serialization converts those bytes to Base64; ZIP serialization writes binary entries. getAsset() returns a detached byte copy, and toJSONDocument() produces the Base64 document object for JSON consumers. The schemas describe serialized files; the internal binary representation does not change them or the content-hash algorithm. See the file API guide.

Readers support ZIP64 and data descriptors within these limits. Writers generate ordinary ZIP files. The tools reject self-extracting prefixes and trailing ZIP data. Browser validation and compression code are embedded in standalone HTML; file processing needs no CDN or service connection. Python is used for independent fixture checks.

The editor loads .pai and .pai.html after validation. HTML import reads only document data; standalone export uses the current editor runtime. Saving produces a browser download and does not automatically overwrite the opened local file. Edits made during file generation remain unsaved.

The reference service uses the same file module. It retains the first uploaded file for each snapshot and renders reading pages using its own runtime.

Required validation ​

LayerChecks
StructureDocument schema; ZIP package schema; required fields, valid ranges, and closed core fields
JSON textUTF-8, valid JSON, unique member names, valid Unicode strings
RelationshipsUnique block and row IDs; each block placed exactly once; valid foreground and background asset references; valid image occurrence IDs and display parameters
AssetsCorrect representation for the container; valid Base64 or readable ZIP entries; matching asset paths and declared lengths
ContainerUnique readable HTML data element; valid ZIP entries, methods, CRC values, and integrity
Conversion and versionsCommon fields and original bytes preserved; packaging-independent hashes; historical snapshots and hashes retained

Passing a schema check does not complete file validation. Implementations MUST also check references, asset bytes, and container rules. Fixed inputs and expected results are available in the fixture directory.
